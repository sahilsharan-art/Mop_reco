# V2 (React) screens: audit against the Streamlit version, and what was changed (25 Nov 2026)

Two independent read-only reviews (API and screens) were run against the code merged as `6f26120`, with the Streamlit dashboard as the baseline; every finding below was read in the code, and the API ones were reproduced where marked. This page records what was FIXED in this change, what is still OPEN, and the speed measured. Server names and credentials are deliberately not written here.

## 1. Speed (full 01/04 - 14/11 run, 45,580 store-days, 5.6M bill lines, development PostgreSQL)

| Request | Before | After | How |
|---|---|---|---|
| Summary | 13.4 s | 4.6 s | the headline and the daily trend read the run's saved per-store-day results instead of counting every bill line; the digital-received figure is `digital_sale - unmatched + manual-only` instead of a SUM over every matched line; the store-day sheet loads as float tuples, not ORM objects |
| Cash (each page) | 4.5 s | 0.35 s | the sheet is built once per (run, period, store, manual-match state) and kept two minutes |
| Float (each page) | 5.2 s | 1.3 s | same |
| `load_fast` (used by the Streamlit Summary too) | 4.4 s | 0.7 s | same loader |
| Notices (new) | - | 2.4 s first, then cached one minute | |

The three engine changes are proved IDENTICAL to the originals, to the paisa: F on all 45,580 store-days, and the verdict and the daily trend for the whole run, each of the eight months, one day and five stores (`scripts/audit_fastpath_equivalence.py --run 2`; tests in `tests/test_v2_perf_fastpaths.py`). The original functions stay in the code as the reference.

## 3. Closed on 25 Nov 2026 (second pass): Float, Summary tables, Exceptions pairing

New API module `app/api_v2_gaps.py` (no engine logic of its own - it shapes `float_tracker`, `store_sheet`, `store_sheet_source`, `queries.match_overview`, `exception_pairing`, `exception_tables`, `manual_match`); new screens `FloatPage`, `SummaryTables`, `ExceptionPairing`; 13 tests in `tests/test_v2_gaps.py`.

* **Float** now matches the Streamlit page: the four tiles (stores above threshold today, total float above, high float with no remark, longest run), the Data-quality section (negative float, and credits exceeding deposits / Defect B with pickup codes and slip numbers read from the run's stored CMS slips, never a raw file), the five views (work queue by default), a remark editor with the system's weekend explanation and the full remark history, bulk upload with a template, a row-by-row check and nothing applied until confirmed, and an export of the chosen view.
* **Summary** gained the two cash statements (cash at store, cash with agency, each with its MISMATCH control), the bills / transactions two-sided tables with the four MISMATCH checks, the store-wise sale-and-cash sheet by date (each date opens onto its stores; the date-equals-sum-of-stores check is shown), the matched bills list with its lag flag and full export, and the controls in full under Data notes (a failing particulars-matrix control is shown above it).
* **Exceptions** is now Exception bills / Exception transactions / Full register / Awaiting Axis. Each open bill carries Txn 1, Amount 1, Txn 2, Amount 2 and More from the ONE global assignment (a transaction is suggested to at most one bill); typing a clean id and pressing Match records the match; two ids that add up to the bill record a split; one id typed against two bills that add up to it records a shared payment; an ambiguous cluster opens a resolver that can pair N bills with N transactions in time order; "Second transaction still open" lists possible duplicate payments; the system's suggestions can be bulk-accepted; the transactions table closes a transaction by typing the bill it paid. Nothing that does not validate is recorded and no override is possible on these routes. Both tables export with the same columns as the screen (never the screen-only ones).
* Checked in a browser against a local copy of run #2 (sign-in, Float tiles / quality / remark editor, Summary tables and a date expanded to its 174 stores, Exceptions with pairing, a refused match showing its named reason).

## 3b. The filled-table upload, closed on 25 Nov 2026 (third pass)

* `POST /exceptions/{bills|transactions}/upload` and the **Upload filled table...** button on both Exceptions tabs (`TableUpload.tsx`). It is the Streamlit
  round trip (CLAUDE.md 6.23): download the table, type the transaction id (bills) or the bill number / refund details (transactions) and remarks, upload the
  SAME file. The engine is `table_upload.py`, unchanged: every row is validated as a typed match is, a transaction already used is refused naming the bill, and
  a file is applied ALL OR NOTHING in one database transaction as one reversible batch.
* **Check, then confirm.** A check writes nothing and returns every acted-on row with its verdict and reasons, plus counts (matches, refunds, remarks). Apply
  needs the confirmation box and the number of acceptable rows the person reviewed; if the file now checks differently the route answers 409 and nothing is written.
  There is no override on this route, a rejected row blocks the whole file, and writes are pinned to the latest completed run.
* **The system's own suggestions travel in the export.** Uploading an untouched export accepts every suggestion in Txn 1 (3,086 on Run #11); above 100 matches the
  dialog says so before the box can be ticked.
* Checked in a browser on a local copy (login, button, file, verdicts, blocked apply) and by 5 tests in `tests/test_v2_gaps.py`. Not applied against any real data.

## 4. Still OPEN (needs a decision or more work; none hidden)

* **Float page-1 detail**: none known. **Exceptions**: no register export of the manual matches, batch-reverse button or date-lag list on this screen (Matching has the first and third). The table upload (the table's own export, filled in) was rebuilt on 25 Nov (third pass, section 3b) and covers the By-transaction batch need: a filled transactions table matches by `matched_bill` or records a refund.
* **Pairing speed**: the first request after a run or a match builds the global assignment (about 55 s on a copy with 110,000 unmapped transactions; a few seconds on Run #5's 6,000) and is then kept five minutes, one build at a time.
* Masters edit has no preview/diff before saving; Upload takes one file (Paytm arrives in parts) and posts it twice (preview, then confirm); Users has no sign-in trail; CMS lacks the bridge / credited-later / ZPO lists and has a NEW override feature that needs Finance sign-off (it overwrites a computed bank-credit figure; rules 3 and 5).
* **Logo**: the supplied CityKart MOP Reco logo is not in V2 (a "CK" tile). The page loads a Google font: self-host it if user PCs have no internet.
* `/store-sheet/export` runs the slow raw-file build inside the request (33 s, unlocked); `/matching` search is a full scan on 5.6M lines; `/float` has no server-side filters; `/cms` and several lists are sent whole and paged in the browser.
* Roles: any signed-in person can edit masters, run, restore and withdraw uploads (parity with Streamlit, section 6.40) - a role design is still needed.
* Not yet measured in production: HTTPS, the proxy, concurrent users. Keep the Streamlit dashboard until a finance user has accepted V2.
